# Краткосрочные сигналы на данных стакана MOEX

Исследовательский проект: предсказывают ли признаки стакана и ленты сделок изменение цены акций Московской биржи на горизонте 5–60 секунд, и остаётся ли что-то от этого сигнала после спреда, комиссии и задержки исполнения.

Стратегия следующая: данные приходят через брокерский API с секундной сеткой, без очереди заявок и без низкой задержки. Проект проверяет саму идею «стакан → прогноз → сделка» в честных условиях частного инвестора. Отрицательный результат здесь тоже результат.

> **Статус.** Конвейер реализован целиком и покрыт тестами (проверен на синтетическом рынке и нарезанных на куски данных одного вечера). Сейчас собираются данные основной торговой сессии. Раздел «Результаты» заполняется после этого, цифры из проверки на синтетике сюда не переносятся.

## Конвейер

```
collect.py  →  prepare.py  →  features.py  →  train.py  →  backtest.py
стрим gRPC     сетка 1 с      признаки и      walk-forward   сделки по bid/ask,
стакан+сделки  (parquet)      цели            валидация      комиссия, задержка
```

| Шаг | Что делает |
|---|---|
| `collect.py` | Подписка на `MarketDataStream` T-Invest API (только чтение): стакан глубиной 10 и лента биржевых сделок. Переподключение при обрыве, запись частями, parquet по дням. |
| `prepare.py` | Равномерная сетка 1 с: состояние стакана на момент `t` (последний снимок не позже `t`), сделки и OFI за интервал `(t−1, t]`. Отбрасывает неконсистентные снимки, устаревший стакан (разрывы данных), аукционы и края сессии. |
| `features.py` | Признаки (только по данным до `t` включительно) и цели (доходность mid вперёд). |
| `train.py` | Walk-forward по дням, Ridge / LogisticRegression / LightGBM с фиксированными гиперпараметрами, бейзлайны, метрики. |
| `backtest.py` | Сделки по ценам стакана с учётом задержки и комиссии, метрики, графики. |
| `run_all.py` | Весь конвейер одной командой. |

## Признаки и цели

Тикеры: SBER, GAZP, LKOH, YDEX, VTBR. Объёмы в лотах, модели обучаются по каждому тикеру отдельно.

- **Стакан в момент `t`:** спред (в тиках и в %), `microprice − mid`, дисбаланс объёмов `(bid − ask) / (bid + ask)` на 1, 5 и 10 уровнях.
- **Динамика в окнах 5, 30, 60 с:** order flow imbalance (Cont et al.), дисбаланс агрессивных сделок «покупки − продажи», прошлая доходность mid, реализованная волатильность.
- **Цель:** `y_h = mid[t+h] / mid[t] − 1`, `h ∈ {5, 30, 60}` с (основные горизонты: 30 и 60 с).
- **Классы для торговли:** `+1` / `−1`, если `|y_h| > θ`, иначе `0`, где `θ = 2·(half_spread + fee)` — полная стоимость круга сделки (спред на входе и выходе плюс комиссия за обе стороны).
- `mid` как признак не используется: абсолютный уровень цены не переносится между днями и тикерами.

Тесты проверяют отсутствие утечки из будущего (портятся все данные после `t`, признаки в строках до `t` не меняются; тест проверен подставленной утечкой) и корректный сдвиг цели.

## Валидация и протокол оценки

- Walk-forward по дням: train — дни `1..k`, test — день `k+1`, без перемешивания. Между train и test отступ 60 с (максимальный горизонт).
- Бейзлайны: нулевой прогноз, «всегда самый частый класс», знак `imbalance_1`.
- Метрики сигнала: IC и Spearman, MAE против нулевого прогноза; для классов — accuracy против бейзлайна, precision / recall по классам.
- Порог `θ`, комиссия и гиперпараметры зафиксированы в коде до анализа реальных данных и не подбираются на тестовых днях.
- Основная конфигурация бэктеста: все тикеры вместе, горизонты 30 и 60 с, задержка 1 с. Остальные задержки, горизонты и комиссии показываются как чувствительность, а не как поиск лучшей комбинации.

## Бэктест

Позиция ±1 лот. Покупка по `ask`, продажа по `bid` из стакана в момент исполнения `t + delay`, поэтому спред учитывается один раз и ровно по данным. Тот же сигнал продлевает удержание, противоположный разворачивает позицию, иначе выход через `h` секунд. Комиссия берётся с оборота на входе и выходе.

- Задержка исполнения: 0 / 1 / 3 / 5 с.
- Комиссия за сторону: 0 / 0,02 / 0,05 / 0,1 % (0,05 % — базовый тариф брокера).
- Метрики: валовый PnL (по mid), PnL после спреда, чистый PnL, число сделок, hit rate, средний PnL на сделку, Sharpe по дням, максимальная просадка и **комиссия безубыточности** — при какой комиссии средний PnL на сделку обнуляется.
- Графики: накопленный PnL (валовый и чистый), чувствительность к задержке и комиссии, распределение PnL на сделку.
- На проверочных данных (синтетика, нарезанные куски) все графики и таблицы помечены `SYNTHETIC / PIPELINE CHECK`, а вид данных определяется по метаданным прогнозов, а не по флагу запуска.

Один из тестов проверяет базовый ориентир: сигнал без информации на плоском рынке с комиссией имеет строго отрицательный PnL.

## Ограничения

- Нет данных об очереди заявок: исполнение моделируется «по рынку» по лучшей цене стакана, без проскальзывания по объёму. Лимитные заявки и выгода от спреда (роль маркет-мейкера) не моделируются.
- Задержка API и сети не измерена: в бэктесте это параметр.
- Мало торговых дней; метки на горизонтах 30–60 с сильно перекрываются, поэтому эффективная выборка намного меньше числа строк. Sharpe по дням — иллюстрация, а не оценка.
- Шаг цены определяется по данным, лотность тикеров различается, поэтому абсолютные объёмы между тикерами не сравниваются.
- Одинаковые сделки с одним временем биржи не дедуплицируются: по данным неясно, дубль это или части одной заявки.

## Запуск

```bash
pip install -r requirements.txt
python run_all.py                    # prepare → features → train → backtest → тесты (на собранных данных)
python run_all.py --pipeline-check   # проверка конвейера без реальных данных
python -m pytest -q                  # тесты
```

Сбор данных (нужен read-only токен T-Invest API, реальные заявки код не выставляет):

```powershell
$env:TINVEST_TOKEN = "<токен>"
$env:TINVEST_CA_BUNDLE = "certs\russian_trusted_root_ca.pem"
python collect.py --minutes 550
```

Серверы T-Invest API подписаны корнем «Russian Trusted Root CA» (Минцифры), которого нет в наборе доверенных корней gRPC. Проект подключает его только к собственному каналу через `TINVEST_CA_BUNDLE`, системные сертификаты не меняются. Клиент сгенерирован из proto-контрактов (`contracts/`, источник в `SOURCE.txt`), официальный SDK не используется.
